# kv_sim — 에이전트 세션의 KV 캐시 유지 정책 시뮬레이터 (C++17)

에이전트는 LLM 호출 → 도구 실행 → LLM 호출을 반복합니다. 도구가 도는 동안 그 세션의 KV 캐시를 **버릴지, 유지할지,
누구 것을 먼저 내보낼지**는 서빙 런타임이 정합니다. 이 시뮬레이터는 실험 3에서 NAT로 잰 실제 호출 트레이스를 재생하면서
그 정책들을 비교합니다.

## 입력과 모델

- `traces.tsv`: `export_trace.py`로 `../nat_langgraph/results_7b`의 **동시 1 실행만** 뽑은 것입니다(세션 48개, LLM 호출 129개).
  동시 1에서는 호출 사이 간격이 큐 대기가 아니라 에이전트 자신의 시간(도구 + 프레임워크)입니다.
  첫 호출의 프롬프트는 약 516토큰이고, 이후 호출은 중앙값 680토큰 중 새 토큰이 60개뿐입니다(92%는 직전 문맥).
- 스텝 단위 시뮬레이션: 매 디코드 스텝마다 실행 중인 호출이 한 토큰씩 만들고, 스텝 길이는
  `ITL(배치) + 그 스텝에 들어온 prefill 토큰 / prefill 속도`입니다. 상수는 같은 GPU에서 잰 값입니다
  (ITL 14.9ms + 시퀀스당 0.44ms, prefill 약 1,400토큰/초, KV 용량 24,064토큰(fp16) / 47,264토큰(fp8)).
- KV는 16토큰 블록 풀(`BlockPool`)에서 할당합니다. 할당은 전부 아니면 전무이고, 유지된 문맥만큼은 다시 prefill하지 않습니다.
- 도구 지연은 측정값 재생 또는 로그정규 분포(계산 0.01초, 조회 0.3초, 웹 검색 3초 등 중앙값 지정)입니다.

| 정책 (`--policy`) | 도구 실행 중 KV | 메모리가 모자랄 때 내보낼 대상 |
|---|---|---|
| `drop` | 즉시 해제 (다음 호출에서 전체 재계산) | — |
| `lru` | 유지 | 가장 오래 쉬고 있는 세션 |
| `hint` | 유지 | 프레임워크 힌트(도구 종류별 예상 지연)상 가장 늦게 돌아올 세션 |
| `oracle` | 유지 | 실제로 가장 늦게 돌아올 세션 (상한선) |

| 입장 제어 (`--admission`) | 동작 |
|---|---|
| `fifo` | 요청 단위 도착 순서. 새 세션도 남의 KV를 내보낼 수 있음 (vLLM 기본과 같은 방식) |
| `session` | 진행 중인 세션의 다음 호출이 먼저. 새 세션은 아무것도 내보내지 않고 들어갈 수 있을 때만 시작 |

`hint`는 NAT 트레이스에 실제로 있는 `NOVA-Predicted-OSL`, `NOVA-Time-To-Next-Event` 같은 에이전트 힌트 필드를
런타임이 받는다고 가정한 것입니다.

## 결과 (시드 5개 중앙값, 세션 지연 p50)

**1. 측정된 문맥 크기(약 700토큰)에서는 메모리가 아니라 연산이 먼저 찹니다.** 내보내기는 한 번도 일어나지 않았고,
LRU·hint·oracle은 같은 값이 나왔습니다. 차이는 유지하느냐 버리느냐뿐입니다.

| 초당 세션 도착 | 0.1 | 0.3 | 0.5 | 0.6 |
|---|---|---|---|---|
| `drop` | 4.9초 | 7.2초 | 12.7초 | **19.9초** |
| `lru` (= hint = oracle) | 3.6초 | 4.1초 | 4.8초 | **5.2초** |

버리면 매 호출 전체를 다시 prefill해야 해서(재계산 비율 100% 대 36%) 같은 부하에서 연산이 먼저 포화됩니다.

**2. 세션마다 긴 공통 문맥(+4,000토큰: 도구 스키마, 검색 문서 등)을 붙이면 KV 용량이 한계가 되고, 정책보다 입장 제어가 결정적입니다.**

| 초당 세션 도착 | 0.05 | 0.1 | 0.15 | 0.2 |
|---|---|---|---|---|
| fp16 KV, `fifo` + `lru` | 9.4초 | 73초 | **3,493초 (붕괴)** | 5,717초 |
| fp16 KV, `fifo` + `oracle` | 9.4초 | 73초 | 3,462초 | 5,692초 |
| fp16 KV, `session` + `lru` | 9.4초 | 12.9초 | **21.7초** | 119초 |
| fp8 용량, `fifo` + `lru` | 9.4초 | 13.2초 | 2,911초 | 5,319초 |
| fp8 용량, `session` + `lru` | 9.4초 | 12.6초 | 19.6초 | 320초 |

- FIFO에서는 새 세션이 도구를 기다리는 세션의 KV를 밀어내고, 밀려난 세션이 돌아와 다시 남을 밀어내는 **스래싱**이 일어납니다.
  0.15에서 재계산 비율이 99.6%가 됩니다. 이때 내보낼 대상을 완벽하게 고르는 oracle도 LRU와 1% 차이밖에 나지 않습니다.
- 새 세션 입장을 미루기만 해도(`session`) 같은 메모리로 감당하는 부하가 약 2배가 됩니다. 이는 KV 용량을 약 2배로 늘린 효과(fp8 용량 + FIFO)보다 큽니다.
- +8,000토큰에서는 fp16 FIFO가 0.1에서 이미 10,238초로 무너지고, fp8 용량 + `session`이 40초로 버팁니다(`out/sweep_pad8000.csv`).

**결론**: 에이전트 서빙에서 KV 관리의 핵심 레버는 "누구를 내보낼까"(eviction 정책)가 아니라
**"새 세션을 언제 받을까"(세션 단위 입장 제어)와 "용량"**입니다. 런타임 스케줄러가 요청이 아니라 세션을 단위로 봐야 한다는 뜻입니다.

## 한계

- fp8 용량 시나리오는 **용량만** 바꾼 것입니다. 실제로 이 GPU에서 스케일 없이 fp8 KV를 쓰면 Qwen2.5-7B의 출력이 깨졌습니다
  (상위 README 실험 3 참고). 정확도가 유지되는 KV 양자화(예: 이상치를 따로 다루는 방식)가 있다는 전제의 값입니다.
- 디코드 비용은 배치 크기만의 선형 함수이고 문맥 길이에 따른 어텐션 비용은 넣지 않았습니다. 긴 문맥 시나리오에서는 지연이 낙관적입니다.
- prefill은 스텝 안에 합쳐 처리하고(chunked prefill 근사), CPU나 CXL 메모리로 내리는(offload) 선택지는 아직 없습니다.
  KV 전송은 턴당 수 MB로 PCIe 기준 1ms 안팎이라, 오프로드 계층을 넣으면 "버림"과 "유지" 사이의 세 번째 선택지가 됩니다.

## 빌드와 실행

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release && cmake --build build -j
./build/test_kv                      # 블록 풀, 희생자 선택, 시뮬레이터 불변식
./sweep.sh                           # out/*.csv 재생성 (BUILD_DIR로 빌드 위치 지정)
# 동시성 검사: cmake -DKV_SIM_SANITIZE=thread (WSL에서는 setarch -R로 실행)
```

스윕의 각 점(정책 × 용량 × 도착률 × 시드)은 독립 시뮬레이션이라, 원자적 인덱스로 일을 나눠 갖는 스레드 풀에서 락 없이 돌립니다.
같은 시드를 정책끼리 공유해서 정책 간 비교는 짝지은 비교입니다.
